# Experimental Zone Dynamics v1

This document defines the first isolated experiment for LICOR's next modeling
branch: explain suspicious zone-optimization shapes by adding braking, apex,
exit, and stint-context variables without replacing the current Spa v2 pipeline.

## Goal

The current offline pipeline models local cost/benefit mostly as:

```text
LICO distance before brake -> fuel saved, time lost
```

The experiment tests whether part of the observed time noise is better explained
by an intermediate chain:

```text
LICO distance
-> approach speed / brake timing / brake shape
-> apex speed / exit speed
-> local time loss
```

## Scope

This branch is intentionally parallel to the current Spa v2 workflow.

- Do not modify Streamlit.
- Do not replace the current `refit_spa_v2.py`.
- Do not overwrite current `data/processed/spa_lmp2_*` artifacts.
- Write all experimental outputs under:

```text
data/processed/experimental/spa_dynamics_v1/
```

## Experimental Files

Experimental code should be clearly labelled and easy to remove:

- `src/licor/analysis/experimental_*`
- `src/licor/reports/experimental_*`
- `scripts/*_experimental.py`

The experiment should not require changes to the current production-style
entrypoints or defaults.

The experiment may add driver-facing companion outputs as long as they stay
under the same experimental directory and do not replace the existing reports.

## Baseline To Preserve

The current comparison baseline is the Spa v2 refit generated by:

- `scripts/refit_spa_v2.py`
- `data/processed/spa_lmp2_zone_piecewise_models.csv`
- `data/processed/spa_lmp2_zone_lico_plan_model_ready.csv`
- `data/processed/spa_lmp2_zone_lico_plan_driver_priors_prudent.csv`
- `data/processed/spa_lmp2_zone_plan_sensitivity.csv`
- `data/processed/spa_lmp2_zone_curve_report.html`
- `data/processed/spa_lmp2_zone_model_report.html`
- `data/processed/spa_lmp2_zone_lico_plan_driver_priors_prudent_report.html`

The experimental script should snapshot the key comparison metrics into a
reference manifest under the experimental output directory so the branch remains
self-documenting even if the main artifacts are later regenerated.

The first pass should stay pragmatic and use metrics already present or easy to

- `lico_distance_before_brake_m`
- `brake_start_m`

- `zone_start_speed_kph`
- `apex_distance_m`

## Non-Goals

This branch does not yet try to:

- replace the current optimizer;
- prove a final ML architecture;
- change the current live-cue export contract;
- generalize cross-circuit automatically.

The goal is to explain whether the missing variables materially improve our
understanding of local time behavior.

## Driver Review Companion

The full dynamics report is expected to stay technical. A simplified companion
report is allowed if it helps a human driver review each zone as a causal chain:

```text
LICO distance -> brake timing -> apex / exit state -> local time cost
```

The simplified report should not hide the data. Its job is to make the current
experimental story easier to evaluate, zone by zone, before any future model
adoption decision.

## Current Reclassification Hypothesis

The current experimental branch is allowed to test a more explicit zone split:

- `T01`, `T08`, `T12-T13` promoted from `diagnostic_only` to experimental
  `model_ready`;
- `T14` reclassified as `micro_lico_only`, meaning the zone is still usable but
  should stay capped to a very small LICO range;
- `T09` remains excluded.

This is still experimental. The branch must preserve both the base status and
the experimental status so the effect on planning can be reviewed directly.

## Adoption Criteria

The experiment is worth keeping only if it produces a clear win on at least one
of these axes:

1. suspicious time/ratio behavior becomes explainable in concrete zone terms;
2. dynamic/context-aware fits explain materially more variance than the current
   one-dimensional view;
3. one or more `diagnostic_only` zones become easier to justify or reject with
   evidence rather than intuition;
4. the experimental audit helps distinguish genuine LICO cost from pilot
   adaptation cost.

If the experiment does not do that, we should remove it and keep the current
pipeline.

## Robust Optimizer v1

The next experimental step is a support-aware optimizer that still reuses the
current planning contract.

The first version should stay intentionally small:

- start from the reclassified experimental zone models;
- derive support-aware penalties from local support mass, nearest observed gap,
  and edge-of-surface proximity;
- optionally use zone-level disagreement between the 1D and dynamics-aware
  views as a bounded uncertainty term;
- write robustified model curves and robust plan outputs beside the current
  experimental artifacts;
- compare naive versus robust selected distances zone by zone.

The long-term goal is to reduce brittle edge optima without hardcoding
zone-specific caps into the optimizer logic.

## Range-Aware Tie-Break v1

The next refinement is allowed to stay additive and sibling to the robust plan:

- keep the existing robust plan outputs intact;
- derive a separate `range-aware` plan only from the robust selected zones and
  their recommended credible ranges;
- prefer the smallest total LICO action that still reaches the global fuel
  target;
- preserve the robust plan as the comparison baseline for this step.

The first comparison is allowed to split into two explicit variants:

- `selected_zones` top-up: only the zones already selected by the robust plan
  may absorb the missing fuel target;
- `all_eligible_zones` top-up: the same floor plan is used, but any eligible
  robust zone may enter as a top-up contributor if that reduces predicted local
  time cost.

This step is not yet the final adaptive optimizer. Its job is simply to answer
whether a range-aware selection naturally avoids brittle point optima without
adding zone-specific caps.

## Lap-By-Lap Replanner v1

The next experimental layer is an offline controller-like simulator, still kept
parallel to the stable pipeline.

The first version should stay intentionally transparent:

- treat the selected experimental plan as a driver-facing static baseline;
- simulate explicit lap events such as full-push openings, under-execution,
  over-execution, and traffic/non-ideal laps;
- consume the existing replay/live `planned vs executed` schema in an offline
  "observed execution replay" mode so the replanner can be stress-tested
  against real laps before any live telemetry loop is added;
- recompute the next-lap fuel demand after each lap;
- compare `static` versus `adaptive` planning from the same scenario script;
- write a lap summary, a per-lap recommended zone table, a scenario summary,
  and a compact HTML report under the same experimental output directory.

This first replanner does not yet model tire regimes or live audio timing. Its
job is to answer whether the project now has enough structure to react
intelligently when the race diverges from the initial fuel plan.

The next race-state variables after this step are expected to include at least:

- fuel-load or stint-mass context, because vehicle mass is a first-order
  performance variable across a stint;
- tire-state regimes, especially for pit-out cold tires and unusually hot track
  conditions;
- later, pit/tire reset effects as part of the same race-state layer.

The first implementation is allowed to stay proxy-based:

- derive lap-level fuel-load state from observed `fuel_start_l` / `fuel_end_l`
  already present in reviewed zone passes;
- convert that into coarse bands such as `heavy`, `medium`, and `light`;
- derive a first tire-regime label from lap-start carcass temperature and
  temperature deltas versus the local baseline;
- attach those fields to replanner outputs before giving them decision power in
  the optimizer itself.

The current experimental implementation has now moved one step beyond pure
reporting:

- a bounded `fuel_load_band` conditioning layer was prototyped, but current
  evidence is not strong enough to keep it as a decision authority;
- `fuel_load_band` and `tire_regime_label` now remain audit/context variables by
  default;
- the current adaptive authority is instead a first execution-calibration layer:
  recent `planned vs executed` fuel/time outcomes can scale the next-lap
  adaptive plan so the replanner reacts to how the driver is actually executing,
  not only to the nominal offline model;
- the next experimental step refines that layer with recent zone-specific
  execution memory, so the replanner can treat "driver under-executes T12-13"
  differently from "driver remains close to model on T18";
- the branch now also exports a validation-oriented handoff preview, so the
  next-lap adaptive recommendation can be inspected in a live-cue-shaped table
  before real live validation starts;
- the branch now also converts that handoff preview back into a replay-ready
  `live_cue_plan`, replays it on the recorded next lap, and writes compact
  per-handoff validation artifacts so the future live cue loop can be judged on
  concrete `lap N -> lap N+1` transitions;
- the branch now also emits a focused `selected_zones_latency_v2` shadow
  adaptive report from the frozen live baseline session, so static versus
  adaptive between-lap deltas can be reviewed before any live authority is
  granted to the controller;
- the branch now also exports two frozen static live-candidate plan CSVs plus a
  first operator-facing pilot protocol in
  `docs/spa_adaptive_live_validation_protocol.md`, so the first driving session
  can start from a fixed selected-zones candidate before true adaptive live
  switching exists;
- the branch now also exports a guarded operator-preview follow-up pack plus
  `docs/spa_adaptive_handoff_preview_playbook.md`, so the next live collection
  step can validate a frozen adaptive handoff before true in-session adaptive
  switching exists;
- the branch now also has a pilot-pack generator and a replay/beep CLI so the
  first live session can start from frozen artifacts, note templates, and
  metadata templates rather than manual file assembly;
- the handoff join now follows the actual next observed lap in sequence rather
  than assuming lap numbers are consecutive, which matters for runs with gaps or
  excluded laps;
- tire-regime labels are still exported for audit and hover/report context, but
  they do not yet modify the plan itself.

Because the project does not yet carry tire-wear telemetry, the next validation
layer is not a tire-wear model. Instead, the branch should export an observed
context-effects audit so fuel-load bands and thermal regimes can be checked
against replayed execution residuals before they are given stronger planning
authority.

## Rollback Strategy

Rollback must be trivial:

- keep all code in explicitly experimental files;
- keep all outputs in the experimental directory;
- do not change existing default paths;
- do not alter the current optimization contract.

If the user wants to abandon the experiment, removing the experimental files and
their outputs should fully restore the previous project behavior.
